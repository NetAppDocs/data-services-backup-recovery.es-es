= Niveles de acceso a archivos de Azure compatibles con NetApp Backup and Recovery

:nofooter: 
:icons: font
:linkattrs:

[role="lead"]
NetApp Backup and Recovery es compatible con el nivel de acceso Azure Archive para clasificar por niveles las copias de seguridad más antiguas y reducir así los costes de almacenamiento. Las copias de seguridad archivadas cuestan más y tardan más en restaurarse, así que revisa los costes de restauración y los tiempos de recuperación antes de clasificar tus copias de seguridad por niveles.



[[supported-azure-blob-access-tiers-for-netapp-backup-and-recovery]]
== Niveles de acceso de Azure Blob compatibles con NetApp Backup and Recovery

Cuando se crean los archivos de backup por primera vez, se almacenan en el nivel de acceso _Cool_. Este nivel está optimizado para almacenar datos a los que se accede con poca frecuencia, pero a los que se puede acceder de forma inmediata cuando sea necesario.

Si tus clústeres de origen ejecutan ONTAP 9.10.1 o una versión posterior, puedes optar por organizar las copias de seguridad en niveles, pasando del almacenamiento _Cool_ a _Azure Archive_ tras un determinado número de días (normalmente más de 30 días), para optimizar aún más los costes. No se puede acceder de forma inmediata a los datos de este nivel cuando los necesites, y su recuperación conlleva un coste mayor, por lo que debes tener en cuenta con qué frecuencia podrías necesitar restaurar datos de estos archivos de copia de seguridad archivados. Consulta la sección de esta página sobre la restauración de datos desde el almacenamiento de archivado.

Al configurar NetApp Backup and Recovery con este tipo de regla de ciclo de vida, no configures ninguna regla de ciclo de vida al configurar el contenedor en tu cuenta de Azure.

https://docs.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview["Obtenga información sobre los niveles de acceso de Azure Blob"^].



[[restore-data-from-archival-storage]]
== Restaurar datos desde el almacenamiento de archivo

Aunque almacenar los archivos de copia de seguridad más antiguos en almacenamiento de archivado es mucho menos caro que el almacenamiento Cool, acceder a los datos de un archivo de copia de seguridad en Azure Archive para las operaciones de restauración lleva más tiempo y cuesta más.

¿Cuánto cuesta restaurar datos desde Azure Archive?:: Hay dos prioridades de restauración que puede elegir al recuperar datos de Azure Archive:
+
--
* *Alto*: Recuperación más rápida, mayor costo
* *Estándar*: Recuperación más lenta, menor costo


Cada método tiene una tarifa de recuperación por GB y una tarifa por solicitud diferentes.  Para conocer los precios detallados de Azure Archive por región de Azure, visite el sitio web https://azure.microsoft.com/en-us/pricing/details/storage/blobs/["Página de precios de Azure"^] .

--



NOTE: No se admite la prioridad alta al restaurar datos desde Azure a los sistemas StorageGRID.

¿Cuánto tiempo tomará restaurar mis datos archivados en Azure Archive?:: Hay dos partes que componen el tiempo de restauración:
+
--
* *Tiempo de recuperación*: el tiempo necesario para recuperar el archivo de copia de seguridad archivado de Azure Archive y colocarlo en el almacenamiento esporádico.  A esto a veces se le llama el tiempo de “rehidratación”.  El tiempo de recuperación es diferente según la prioridad de restauración que elija:
+
** *Alto*: < 1 hora
** *Estándar*: < 15 horas


* *Tiempo de restauración*: el tiempo para restaurar los datos del archivo de respaldo en el almacenamiento Cool.  Esta vez no es diferente a la operación de restauración típica directamente desde el almacenamiento Cool, cuando no se utiliza un nivel de archivo.
+
Para obtener más información sobre las opciones de recuperación de Azure Archive, consulte https://azure.microsoft.com/en-us/pricing/details/storage/blobs/#faq["Preguntas frecuentes sobre Azure"^] .



--


[NOTE]
====
Restaurar un volumen o un archivo desde el almacenamiento de archivo puede tomar tiempo adicional. El trabajo permanece *In progress* en el Job Monitor mientras Backup and Recovery vuelve a intentar la restauración según la prioridad seleccionada. Supervisa la restauración en el *Job Monitor*; se completa cuando el trabajo alcanza un estado final, como *Completed* o *Failed*, después de todos los intentos de reintento. No inicies otra restauración a menos que el trabajo falle definitivamente.
