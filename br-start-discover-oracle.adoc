[[configure-dns-for-air-gapped-host-discovery-in-netapp-console-local-deployment]]
== Configura DNS para el descubrimiento de hosts aislados en la implementación local de NetApp Console

Si estás utilizando NetApp Console en una implementación local en un entorno aislado (air-gapped) donde los hosts de bases de datos no son accesibles a través del DNS estándar, necesitas modificar temporalmente la configuración interna de RKE2 CoreDNS. Esto permite que los pods resuelvan nombres de host específicos a direcciones IP dentro del clúster, de forma similar a añadir entradas a `/etc/hosts` en un nodo.


IMPORTANT: Antes de realizar cambios, comprueba tanto la configuración actual de CoreDNS como el archivo existente `rke2-coredns-config.yaml` HelmChartConfig para evitar sobrescribir cualquier personalización ya existente. En la mayoría de los nodos de implementación local de NetApp Console, este archivo ya existe y ya contiene solicitudes de recursos. Si el archivo ya existe, no lo vuelvas a crear; en su lugar, añade únicamente el bloque `servers:` al `valuesContent` existente. Aplica este cambio usando los manifiestos de RKE2 para que el operador y el runtime de RKE2 sigan gestionándolo de forma coherente.

.Antes de empezar
* Siempre que sea posible, mantén el archivo HelmChartConfig bajo control de cambios.
* Utiliza un nombre de archivo claro para que el propósito de la sustitución de CoreDNS sea obvio.
* Si el registro DNS esperado no aparece en el archivo Corefile, comprueba los registros del servidor RKE2 y confirma la sintaxis del archivo de manifiesto.


.Pasos
. Comprueba la configuración actual de CoreDNS para asegurarte de que no estás anulando un cambio ya realizado:
+
[source, shell]
----
kubectl -n kube-system get cm rke2-coredns-rke2-coredns -o jsonpath='{.data.Corefile}'
----
. Comprueba que el archivo HelmChartConfig existe:
+
[source, shell]
----
sudo cat /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
+
[role="tabbed-block"]
====
.Si el archivo existe
--
.. Ejecuta el siguiente script para añadir el  `servers:` bloque al archivo HelmChartConfig ya existente:
+
[source, shell]
----
MANIFEST=/var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml

# 1. Back up first
sudo cp -a "$MANIFEST" "$MANIFEST.bak.$(date +%Y%m%d-%H%M%S)"

# 2. Safety checks: valuesContent must be the last key, no servers: block yet
grep -n 'servers:' "$MANIFEST"        # must return nothing
tail -c 1 "$MANIFEST" | od -c | head  # file must end with a newline

# 3. Append ONLY the servers block (nothing above it changes)
sudo tee -a "$MANIFEST" >/dev/null <<'YAML'
    servers:
    - zones:
      - zone: .
      port: 53
      plugins:
      - name: errors
      - name: health
        configBlock: |-
          lameduck 10s
      - name: ready
      - name: kubernetes
        parameters: cluster.local in-addr.arpa ip6.arpa
        configBlock: |-
          pods insecure
          fallthrough in-addr.arpa ip6.arpa
          ttl 30
      # ───────────────────────── EDIT BELOW ─────────────────────────
      # Static DNS records for hosts the corporate DNS cannot resolve.
      # Format:  <IP>  <FQDN>  [optional aliases...]
      # `fallthrough` MUST stay as the last line -- it lets every other
      # name go to the upstream resolver via the `forward` plugin below.
      - name: hosts
        configBlock: |-
          1.2.3.4 example.domain.com exampleshortname
          fallthrough
      # ───────────────────────── EDIT ABOVE ─────────────────────────
      - name: prometheus
        parameters: 0.0.0.0:9153
      - name: forward
        parameters: . /etc/resolv.conf
      - name: cache
        parameters: 30
      - name: loop
      - name: reload
      - name: loadbalance
YAML

# 4. Confirm the merged result
sudo cat "$MANIFEST"
----
.. Comprueba que el único cambio en el archivo HelmChartConfig sea la incorporación del bloque  `servers:`.


--
.Si el archivo no existe
--
.. Edita el área  `configBlock` del siguiente script y añade tus registros DNS estáticos. Esto crea un archivo YAML HelmChartConfig en la carpeta manifests de RKE2, que RKE2 aplica automáticamente para anular la configuración de CoreDNS:
+
[source, shell]
----
sudo tee /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml >/dev/null <<'YAML'
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-coredns
  namespace: kube-system
spec:
  # NOTE: This is a HelmChartConfig that *overlays* values onto the rke2-coredns
  # HelmChart already managed by RKE2. RKE2 watches /var/lib/rancher/rke2/server/manifests
  # and will re-render the rke2-coredns Helm release whenever this file changes.
  #
  # The `servers:` list below REPLACES the chart's default server definition,
  # so every plugin that was in the stock Corefile must be present here.
  # Do NOT delete plugins you don't recognize -- they are required for cluster DNS.
  valuesContent: |-
    servers:
    - zones:
      - zone: .
      port: 53
      plugins:
      - name: errors
      - name: health
        configBlock: |-
          lameduck 10s
      - name: ready
      - name: kubernetes
        parameters: cluster.local in-addr.arpa ip6.arpa
        configBlock: |-
          pods insecure
          fallthrough in-addr.arpa ip6.arpa
          ttl 30
      # ───────────────────────── EDIT BELOW ─────────────────────────
      # Static DNS records for hosts the corporate DNS cannot resolve.
      # Format:  <IP>  <FQDN>  [optional aliases...]
      # `fallthrough` MUST stay as the last line -- it lets every other
      # name go to the upstream resolver via the `forward` plugin below.
      - name: hosts
        configBlock: |-
          1.2.3.4 example.domain.com exampleshortname
          fallthrough
      # ───────────────────────── EDIT ABOVE ─────────────────────────
      - name: prometheus
        parameters: 0.0.0.0:9153
      - name: forward
        parameters: . /etc/resolv.conf
      - name: cache
        parameters: 30
      - name: loop
      - name: reload
      - name: loadbalance
YAML
sudo chmod 600 /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
.. Copia y ejecuta el script.


--
====
. Comprueba que CoreDNS haya detectado el cambio:
+
[source, shell]
----
kubectl -n kube-system get cm rke2-coredns-rke2-coredns -o jsonpath='{.data.Corefile}'
----
+
Si el cambio no se aprecia al cabo de unos minutos, reinicia la implementación de CoreDNS y luego vuelve a comprobar el archivo Corefile:

+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----
. Si necesitas eliminar las entradas después de descubrir los hosts de la base de datos, haz lo siguiente:
+
[role="tabbed-block"]
====
.Si añadiste datos al final de un archivo existente
--
.. Restaura el archivo de copia de seguridad o elimina únicamente el bloque  `servers:` del archivo:
+
[source, shell]
----
sudo cp -a /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml.bak.<timestamp> \
/var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
+
No borres el archivo, porque contiene la configuración existente del recurso RKE2.

.. Después de restaurar el archivo, elimina las entradas de host. Las entradas obsoletas pueden causar problemas en la detección de hosts y en las copias de seguridad programadas.
.. Reinicia la implementación de CoreDNS:
+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----


--
.Si has creado un archivo nuevo
--
.. Elimina el archivo HelmChartConfig de la carpeta manifests:
+
[source, shell]
----
sudo rm /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
.. Tras eliminar el archivo, borra las entradas de host. Las entradas obsoletas pueden provocar problemas en la detección de hosts y en las copias de seguridad programadas.
.. Reinicia la implementación de CoreDNS:
+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----


--
====




[[add-an-oracle-database-host-and-discover-resources]]
== Añade un host de base de datos Oracle y descubre recursos

Añade la información del host de la base de datos Oracle y deja que NetApp Backup and Recovery descubra las cargas de trabajo. Para cada agente de Console, selecciona los sistemas que quieres descubrir.

.Pasos
. En el menú de la NetApp Console, selecciona *Protección* > *Backup and Recovery*.
. En *Cargas de trabajo*, seleccione el mosaico *Oracle*.
. Seleccione *Descubrir recursos*.
. Selecciona *Oracle* para el campo *Tipo de carga de trabajo*.
. Si aún no has almacenado credenciales para este host de Oracle Database, selecciona *Add credentials*.
+
.. Seleccione el agente de consola que se utilizará con este host.
.. Introduzca un nombre para esta credencial.
.. Introduzca el nombre de usuario y la contraseña de la cuenta.
.. Seleccione *Listo*.


. *Registro de host*: Añade un nuevo host de Oracle Database. En el campo *FQDN o dirección IP del host*, introduce el FQDN o la dirección IP del host. Para bases de datos en clúster, puedes introducir el FQDN o la dirección IP de cualquier nodo del clúster. Luego proporciona las credenciales, el agente de la Console y el número de puerto.
. (Opcional) Si eliges credenciales para un usuario que no es root, haz lo siguiente:
+
.. Para obtener instrucciones sobre cómo añadir el usuario no raíz seleccionado al archivo sudoers en el host de la base de datos Oracle, selecciona *Configurar sudoers*.
.. Sigue las instrucciones en el cuadro de diálogo, activa la casilla cuando termines y selecciona *Done*.


. *Configuración avanzada*: haz lo siguiente:
+
.. Introduce el puerto y la ruta de instalación que quieres usar para el NetApp plug-in. El plug-in permite la comunicación entre el host de la base de datos Oracle y NetApp Backup and Recovery.
.. Elige si quieres permitir que NetApp Backup and Recovery instale el complemento automáticamente en cada host o saltar la instalación automática del complemento para todos los hosts. Selecciona *Muéstrame cómo* para ver las instrucciones de instalación manual.
+
[NOTE]
====
NetApp Backup and Recovery se conecta a cada host a través de SSH para instalar el complemento automáticamente. Activa *Usar instalación manual* cuando se dé alguna de las siguientes circunstancias:

*** Uno o más hosts no están ejecutando el servicio SSH.
*** Cualquier host ya dispone del complemento NetApp (incluso si solo lo tienen algunos miembros del clúster).
*** Prefieres instalar el plug-in en cada host manualmente.


====
.. Si el host de la base de datos está en clúster, activa la opción *Add all hosts in the cluster* para descubrir todos los hosts del clúster.
.. Elige si quieres ejecutar comprobaciones de preinstalación en cada host antes de instalar automáticamente el plug-in. Si las comprobaciones fallan, se detiene la instalación automática del plug-in. Para omitir las comprobaciones e instalar de todos modos, activa *Skip optional preinstall checks* (se activa automáticamente si eliges la instalación manual).


. Seleccione *Descubrir*.
+

TIP: Añadir recursos puede tardar varios minutos. Para ver el progreso, selecciona *Seguir el progreso* en el cuadro de diálogo de estado en la parte inferior de la página de Inventario o selecciona *Supervisión* en la navegación de la izquierda.



.Resultado
La carga de trabajo de Oracle Database aparece en la lista de cargas de trabajo en la página de Inventario.



[[continue-to-the-netapp-backup-and-recovery-dashboard]]
== Continuar al panel de control de NetApp Backup and Recovery

. En el menú de la NetApp Console, selecciona *Protección* > *Backup and Recovery*.
. Selecciona un mosaico de carga de trabajo (por ejemplo, Oracle Database).
. Desde el menú Copia de seguridad y recuperación, seleccione *Panel de control*.
. Comprueba el estado de la protección de datos. El número de cargas de trabajo en riesgo o protegidas aumenta en función de las cargas de trabajo recién detectadas, protegidas y respaldadas.
