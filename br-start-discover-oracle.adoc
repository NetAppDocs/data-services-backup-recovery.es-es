[[configure-dns-for-air-gapped-host-discovery-in-netapp-console-local-deployment]]
== Configura DNS para el descubrimiento de hosts aislados en la implementación local de NetApp Console

Si estás utilizando una implementación local de NetApp Console en un entorno aislado (air-gapped) en el que los hosts de bases de datos no son accesibles a través del DNS estándar, debes modificar temporalmente la configuración interna de RKE2 CoreDNS. Esto permite que los pods resuelvan nombres de host específicos a direcciones IP dentro del clúster, de forma similar a añadir entradas a `/etc/hosts` en un nodo.


IMPORTANT: Antes de realizar cambios, comprueba la configuración actual de CoreDNS para evitar sobrescribir cualquier personalización existente. Utiliza los manifiestos de RKE2 para aplicar este cambio, asegurándote de que el operador y el runtime de RKE2 lo gestionen de forma coherente.

.Antes de empezar
* Siempre que sea posible, mantén el archivo HelmChartConfig bajo control de cambios.
* Utiliza un nombre de archivo claro para que el propósito de la sustitución de CoreDNS sea obvio.
* Si el registro DNS esperado no aparece en el archivo Corefile, comprueba los registros del servidor RKE2 y confirma la sintaxis del archivo de manifiesto.


.Pasos
. Comprueba la configuración actual de CoreDNS para asegurarte de que no estás anulando un cambio ya realizado:
+
[source, shell]
----
kubectl -n kube-system get cm rke2-coredns-rke2-coredns -o jsonpath='{.data.Corefile}'
----
. Copia el siguiente bloque de comandos y edita el área  `configBlock` para añadir tus registros DNS estáticos. Esto crea un archivo YAML HelmChartConfig en la carpeta manifests de RKE2, que RKE2 aplica automáticamente para anular la configuración de CoreDNS:
+
[source, shell]
----
sudo tee /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml >/dev/null <<'YAML'
apiVersion: helm.cattle.io/v1
kind: HelmChartConfig
metadata:
  name: rke2-coredns
  namespace: kube-system
spec:
  # NOTE: This is a HelmChartConfig that *overlays* values onto the rke2-coredns
  # HelmChart already managed by RKE2. RKE2 watches /var/lib/rancher/rke2/server/manifests
  # and will re-render the rke2-coredns Helm release whenever this file changes.
  #
  # The `servers:` list below REPLACES the chart's default server definition,
  # so every plugin that was in the stock Corefile must be present here.
  # Do NOT delete plugins you don't recognize -- they are required for cluster DNS.
  valuesContent: |-
    servers:
    - zones:
      - zone: .
      port: 53
      plugins:
      - name: errors
      - name: health
        configBlock: |-
          lameduck 10s
      - name: ready
      - name: kubernetes
        parameters: cluster.local in-addr.arpa ip6.arpa
        configBlock: |-
          pods insecure
          fallthrough in-addr.arpa ip6.arpa
          ttl 30
      # ───────────────────────── EDIT BELOW ─────────────────────────
      # Static DNS records for hosts the corporate DNS cannot resolve.
      # Format:  <IP>  <FQDN>  [optional aliases...]
      # `fallthrough` MUST stay as the last line -- it lets every other
      # name go to the upstream resolver via the `forward` plugin below.
      - name: hosts
        configBlock: |-
          1.2.3.4 example.domain.com exampleshortname
          fallthrough
      # ───────────────────────── EDIT ABOVE ─────────────────────────
      - name: prometheus
        parameters: 0.0.0.0:9153
      - name: forward
        parameters: . /etc/resolv.conf
      - name: cache
        parameters: 30
      - name: loop
      - name: reload
      - name: loadbalance
YAML
sudo chmod 600 /var/lib/rancher/rke2/server/manifests/rke2-coredns-config.yaml
----
. Comprueba que CoreDNS haya detectado el cambio:
+
[source, shell]
----
kubectl -n kube-system get cm rke2-coredns-rke2-coredns -o jsonpath='{.data.Corefile}'
----
+
Si el cambio no se aprecia al cabo de unos minutos, reinicia la implementación de CoreDNS y luego vuelve a comprobar el archivo Corefile:

+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----
. Si necesitas eliminar las entradas después de descubrir los hosts de la base de datos, haz lo siguiente:
+
.. Elimina el archivo HelmChartConfig de la carpeta manifests.
.. Reinicia la implementación de CoreDNS:
+
[source, shell]
----
kubectl -n kube-system rollout restart deploy/rke2-coredns-rke2-coredns
----






[[add-an-oracle-database-host-and-discover-resources]]
== Añade un host de base de datos Oracle y descubre recursos

Agregue información del host de Oracle y permita que NetApp Backup and Recovery descubra cargas de trabajo. Dentro de cada agente de consola, seleccione los sistemas en los que desea descubrir cargas de trabajo.

.Pasos
. Desde el menú de la NetApp Console , seleccione *Protección > Copia de seguridad y recuperación*.
. En *Cargas de trabajo*, seleccione el mosaico *Oracle*.
. Seleccione *Descubrir recursos*.
. Selecciona *Oracle* para el campo *Tipo de carga de trabajo*.
. Si aún no has almacenado credenciales para este host de Oracle Database, selecciona *Add credentials*.
+
.. Seleccione el agente de consola que se utilizará con este host.
.. Introduzca un nombre para esta credencial.
.. Introduzca el nombre de usuario y la contraseña de la cuenta.
.. Seleccione *Listo*.


. *Registro de host*: Añade un nuevo host de Oracle Database. En el campo *Host FQDN or IP address*, introduce el FQDN o la dirección IP del host; para bases de datos en clúster puedes introducir el FQDN o la IP de cualquier nodo del clúster. Luego proporciona las credenciales, el agente de la Console y el número de puerto.
. (Opcional) Si eliges credenciales para un usuario que no es root, haz lo siguiente:
+
.. Para obtener instrucciones sobre cómo agregar el usuario no root que seleccionaste al archivo sudoers en el host de Oracle Database, selecciona *Configure sudoers*.
.. Sigue las instrucciones en el cuadro de diálogo, activa la casilla cuando termines y selecciona *Done*.


. *Configuración avanzada*: haz lo siguiente:
+
.. Introduce el puerto y la ruta de instalación que quieres usar para el NetApp plug-in. El plug-in permite la comunicación entre el host de la base de datos Oracle y NetApp Backup and Recovery.
.. Elige si quieres permitir que NetApp Backup and Recovery instale el complemento automáticamente en cada host o saltar la instalación automática del complemento para todos los hosts. Selecciona *Muéstrame cómo* para ver las instrucciones de instalación manual.
+
[NOTE]
====
Backup and Recovery se conecta a cada host a través de SSH para instalar el complemento automáticamente. Activa *Usar instalación manual* cuando se dé cualquiera de los siguientes casos:

*** Uno o más hosts no están ejecutando el servicio SSH.
*** Cualquier host ya dispone del complemento NetApp (incluso si solo lo tienen algunos miembros del clúster).
*** Prefieres instalar el plug-in en cada host manualmente.


====
.. Si el host de la base de datos está en clúster, activa la opción *Add all hosts in the cluster* para descubrir todos los hosts del clúster.
.. Elige si quieres ejecutar comprobaciones de preinstalación en cada host antes de instalar automáticamente el plug-in. Si las comprobaciones fallan, se detiene la instalación automática del plug-in. Para omitir las comprobaciones e instalar de todos modos, activa *Skip optional preinstall checks* (se activa automáticamente si eliges la instalación manual).


. Seleccione *Descubrir*.
+

TIP: Añadir recursos puede llevar varios minutos. Para ver el progreso, selecciona *Seguir progreso* en el cuadro de diálogo de estado en la parte inferior de la página de Inventario o selecciona *Supervisión* en el menú de la izquierda.



.Resultado
La carga de trabajo de Oracle Database se muestra en la lista de cargas de trabajo en la página Inventory.



[[continue-to-the-netapp-backup-and-recovery-dashboard]]
== Continuar al panel de control de NetApp Backup and Recovery

. Desde el menú de la NetApp Console , seleccione *Protección* > *Copia de seguridad y recuperación*.
. Seleccione un mosaico de carga de trabajo (por ejemplo, Microsoft SQL Server).
. Desde el menú Copia de seguridad y recuperación, seleccione *Panel de control*.
. Revisar la salud de la protección de datos.  La cantidad de cargas de trabajo en riesgo o protegidas aumenta según las cargas de trabajo recientemente descubiertas, protegidas y respaldadas.
